# Coder Next на слабом железе: статика на карте, уровни экспертов, предсказатель

Дата: 3 сентября 2026. Утверждено пользователем в этот же день.
Контекст и все измерения: `HANDOFF_ROUTER.md`, `STATE.md`. Правила проекта (замер вместо
утверждения, контроль обязателен, инструмент печатает что НЕ измерил, сборка только через
`bench/build_safe.ps1`, замеры под `bench/lock.ps1`, коммит в оба репозитория) действуют без
исключений.

Проверено по самим GGUF-файлам 3 сентября, доки в этих местах устарели:

| эксперты IQ4_XS | 42,68 ГБ | **33,38 ГиБ** (gate/up IQ3_S 220 МиБ, down IQ4_XS 272 МиБ на слой; эксперт 1,39 МиБ) |

Vulkan-бэкенд форка умеет mul_mat/mul_mat_vec для Q6_K, Q8_0, IQ2_S, IQ3_S, IQ3_XXS, IQ4_XS.
Отсутствуют операции только над активациями: `SSM_CONV`, `DELTA_NET`, `SOFTPLUS`, `EXP`;
`L2_NORM` — шейдер собран, точки подключения закомментированы.

## Диагноз

164 мс/токен (прогретый кэш) и 337 (холодный) при потолке 101 мс в ОЗУ. Вся разница —
подкачка с механического D: (23,3 мс за случайное чтение). Голова на карте дала 0 % именно
поэтому. Порядок рычагов: (1) убрать подкачку, (2) убрать статику с шины ОЗУ, (3) только потом
проценты покрытия.

Ключевое следствие: статика на карте не только снимает ~74 мс с шины. Она освобождает
1,7 ГиБ (IQ3_XXS) / 2,4 ГиБ (IQ4_XS) ОЗУ, после чего эксперты IQ3_XXS (24,6 ГиБ) влезают
целиком, а у IQ4_XS резидентно ~80 % экспертов, где по кривой покрытия промахов ~0,1 на токен.

Оценки (проверяются замером, не принимаются): IQ3_XXS ≈ 55–60 мс/токен (~17 ток/с);
IQ4_XS ≈ 70 мс (~14 ток/с).

## Пять шагов

### 1. Ноль кода
- Скопировать `D:\Qwen3-Coder-Next-UD-IQ3_XXS.gguf` на `C:\models\` (останется ~12 ГБ).
- Снять след маршрутизации (команда в HANDOFF_ROUTER.md §6) на 1900 токенов, с копии на C:.
  Бинарник от 3 сентября уже содержит `MEMEX_EXPERT_TRACE`; правка в `memex-fwd.cpp`
  незакоммичена — закоммитить как есть.
- Перемерить `--gen 8` на копии с C: против D:, чередуя плечи, три круга.

### 2. Реестр архитектур
Сейчас в `memex-fwd.cpp` девять мест выбирают построитель тернарником
(строки ~5355, 7046, 7537, 7548, 8052, 8093, 8207, 8275, 8359), а полный диспетчер один —
`Generator::build_one` (~3800). Три места имеют только две ветки: новая архитектура попадает
в чужой построитель и получает работающий граф с другим ответом.

Дизайн: одна структура `ArchModel` (какие веса заполнены, какой построитель, нужен ли
`DeltaState`, есть ли карта для слоёв) и одна функция `build_any(...)`, через которую идут
все девять точек. Если архитектура не поддержана в данной точке — **отказ вслух** с именем
точки, а не тихий откат. Загрузчик тоже сводится к одной таблице «имена тензоров → поля».
Проверка: `--decode-check 16` на трёх моделях (qwen3moe mx1, gemma4, qwen3next) даёт те же
токены, что до правки; `--gen 8` на mx1 не медленнее (19,7 ток/с ± разброс).

### 3. Вся статика на карту для декода (n_tokens = 1)
Префилл остаётся на CPU как есть. Карточный граф слоя строится только для одного токена.

3a. Vulkan (файлы `ggml/src/ggml-vulkan.cpp`, `ggml/src/vulkan-shaders/`):
- `SSM_CONV` для одного токена: 4 отвода × 8192 каналов, читает окно состояния 3×8192.
- `SOFTPLUS` (унарная) и `EXP` (если понадобится для композиции).
- `L2_NORM`: раскомментировать подключение, проверить.
- `DELTA_NET` для одного токена: на голову S[128×128] f32, k, q, v, decay, beta →
  out и новое S (формула в комментарии `qwen35_delta_layer`, memex-fwd.cpp ~3350). Один
  диспатч на слой, 32 головы, `repeat_type` 0 и 1 оба поддержать.
- Проверка каждой операции `test-backend-ops` против CPU в форматах и размерах именно этой
  модели; порог сравнения печатается.

3b. `gpu_static`: слой дельта-сети (норма → qkv/gate/ba → conv → l2 → delta → norm·gate → out)
и 12 слоёв внимания с `rope_multi` секции {11,11,10,0}, `n_rot 64 < head_dim 256`,
`t_pos_` размером [4W]; KV только для 12 слоёв; `DeltaState` на карте (72 МиБ), состояние
пишется на карте, снимок/восстановление для развёртки не требуется (развёртка для этой
архитектуры остаётся запрещённой вслух). Маршрутизатор `ffn_gate_inp` и общий эксперт — на
карте. Граница с CPU — два пересечения на слой: скрытое состояние вниз перед экспертами,
результат экспертов вверх.
- Бюджет видеопамяти печатается собственным учётом: статика 1,72/2,41 ГиБ + KV + состояние
  + рабочие буферы ≤ 3,5 ГиБ; каждый буфер > 256 МиБ либо явно вне BAR (строка `ne BAR`).
- Сверка: побайтовая (`--gpu-static-verify`), зонд одного слоя против `Qcur_roped-3`
  процессорного построителя, `--decode-check 16` на IQ3_XXS, затем на IQ4_XS.
- Замер: `--gen 8`, плечи карта/CPU чередуются, три круга, разброс рядом со средним,
  на IQ3_XXS с C: и на IQ4_XS с D:.


### 3c. Находки ревью горячего пути (3 сентября, вечер) — добавлено к плану
Ревью кода (только чтение) поправило оценки и добавило рычаги; каждый идёт через замер:
- **Скорость карты для Q6_K — 67,6 ГБ/с, не 127** (голова 243,4 МиБ за 3,774 мс). Статика на
  карте стоит ~34 мс, а не 15–18; выигрыш шага 3 ≈ 40 мс/токен. Шейдер `mul_mat_vec` q6_K
  упирается в себя — отдельный кандидат на разбор.
- **Эксперты IQ3_XXS/IQ2_S на CPU ограничены портом 5, не полосой** (~16 и ~22 ГБ/с на 4 ядрах);
  реальная цена ~26,5 мс, потолок в ОЗУ ~107 мс. Репак `IQ3_XXS_R4`/`IQ2_S_R4` есть в форке,
  работает с `mul_mat_id`, требует приватной памяти — **встроить в резидентное хранилище шага 4**.
- **Барьеры пула потоков**: `cgraph->n_batch` не задаётся ⇒ ~2200 барьеров/токен идут через
  OpenMP-барьер MSVC вместо собственного спина (`ggml.c:4608-4623`). Замер `IK_PRINT_TIMING`,
  затем A/B с `n_batch = 64`. Ожидание 2–7 мс, риск нулевой. Тот же замер отвечает на вопрос
  `-t 4/6/8` (свип с чередованием).
- **Загрузчик под Windows зовёт `PrefetchVirtualMemory` на весь файл** (`llama-mmap.cpp:477-480`,
  `prefetch = -1`): 26,5 ГБ последовательно с HDD при каждом старте. Нужен флаг отключения и
  замер времени загрузки.
- **`ggml-moe-prefetch` собран только под Linux** (`ggml-moe-prefetch.cpp:3`), крючки в `mul_mat_id`
  стоят. Порт на `PrefetchVirtualMemory` — самый дешёвый путь к предзагрузке шага 4/5.
- **Маршрутизатор f32 → q8_0** (−5,9 мс): сначала офлайн по дампу скрытых состояний — совпадение
  множеств top-10 послойно; в модель только через `llama-quantize --custom-q` и `--decode-check 16`.
- Дефекты к исправлению: безусловная копия маршрутизации в `build_qwen35_step` (48 узлов, →
  под флаг, отдано агенту шага 2); откат буфера карты с host-visible на device-local **молчит**
  (`ggml-vulkan.cpp:1917-1936`) — превращает каждый `tensor_set` в submit+ожидание, обязан
  отказывать вслух (в 3b); аллокации на токен в `set_step` (`gpu_static.cpp:1611,1665`).
- Хвост первых появлений (лаборатория, след 1900 токенов): **1,4 % обращений идут к экспертам,
  ещё не встречавшимся в документе**, плато 98,6 % при любом бюджете. Частота/LRU/межслойный их
  не достают. Отсюда обязательны затравка с чужих текстов (следы снимаются) и предсказатель по
  скрытому состоянию (R0: маршрутизатор слоя l+k на состоянии слоя l; `bench/hidden_lab.py`).
- Цена промаха измерена (`bench/io_miss_cost.py`): SSD 2,74 мс за эксперта 1,03 МиБ, полоса
  310–415 МБ/с **не растёт с глубиной очереди**; HDD 21 мс, mmap-промах равен прямому чтению.
  SSD-уровень даёт ≤ ~38 экспертов на токен при 100 мс/токен; HDD как уровень бесполезен.

### 4. Уровни ОЗУ → SSD → HDD для экспертов
- `ResidentSet` учится считать общего эксперта как статический трафик (он на карте после
  шага 3, и это надо отражать в знаменателе).
- Резидентность по частоте **на слой**, окно по документу, обновление раз в N токенов.
  Резидентные эксперты закреплены в ОЗУ (собственный буфер, не mmap), остальные читаются
  с уровня, где лежат: копия «холодной» части на C: если место есть, иначе HDD.
- Инструмент печатает: долю попаданий на следующий токен по слоям, число чтений с SSD и с
  HDD за токен, сколько экспертов **пропущено** (должно быть 0: режим «ждать», ответ не
  меняется; режим «пропустить» существует только с явным флагом и печатью счётчика).
- Проверка кривой покрытия на самом IQ4_XS до выводов.

#### Параметры шага 4 по симуляции (3 сентября, вечер, `bench/system_sim.py`)
Резидентность C по доступной ОЗУ; затравка счётчиков с калибровочного корпуса (пока три чужих
текста, 2300 токенов — расширить); обновление набора раз в 16 токенов; предзагрузка B=16 экспертов
слоя l+4 по R1 (маршрутизатор слоя l+4 на состоянии слоя l + поправка 513×512, ~2 МиБ f16 на
модель). Ожидание: при C=410 — 0,55 синхронных промаха на токен (2,6 на холодном старте, 0,26 в
установившемся режиме ≈ 1 мс), 6 чтений SSD на токен при бюджете 26; при C=320 — 1,23 / 6,0 /
0,52. B=32 превышает полосу SSD. Проверяется в движке, не принимается.

### 5. Предсказатель как предзагрузчик
- Признаки: скрытое состояние после слоя l (копия `ffn_norm`, уже читается с карты) и
  история экспертов последних N токенов. Цель: множество экспертов слоя l+k на этом и
  следующем токене.
- Сначала офлайн в `bench/route_predict.py`: обучаемые варианты (линейный на скрытом
  состоянии, малый MLP) против частоты; метрики отдельно на первых 200 токенах (холодный
  старт) и по худшему слою; стоимость предсказателя в мс считается отдельно.
- В C++ только победивший вариант, как один matmul [2048×512] на слой на карте.
- Сверка `--decode-check 16`: предсказание не меняет ответ ни на один токен.
