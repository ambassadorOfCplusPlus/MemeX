## 0. Постановка и главный вывод

Сейчас все наши механизмы живут в исследовательском харнессе `examples\memex-fwd\memex-fwd.cpp`
(~9400 строк). У харнесса нет ничего продуктового: только argmax вместо семплера, нет HTTP/API,
нет потокового вывода, нет очереди запросов и слотов, нет продолжения диалога, нет сдвига контекста,
он Windows-only и с вшитыми числами карты.

Задача — **не писать свой сервер, а встроить наши механизмы как ОПЦИИ в штатный `llama-server`**
того же форка. Ключевые находки анализа:

1. Штатный сервер форка даёт даром почти всю продуктовую обвязку: OpenAI + Anthropic + Responses
   API, полный набор семплеров, непрерывный батчинг со слотами, SSE-стриминг, кэш промптов,
   сдвиг контекста, спекулятивный декод, кроссплатформенность через cpp-httplib.
2. Харнесс уже устроен как «граф + опции»: единая точка `build_any(ArchModel, Graph*, ..., BuildOpts)`
   принимает все механизмы указателями (`gstat`, `gx`, `rs`, `es`, `ds`, `zc`). Это ровно тот
   контракт, который надо перенести в билдер ядра.
3. **В ядре форка уже есть заготовки наших механизмов** (открыто агентом-исследователем):
   пространство имён `memex_cc` (резидентный бонус к выбору экспертов), отложенная/потоковая
   загрузка экспертов (`llama-expert-io.h` + `expert_tensor_index`), cparam `prefetch_experts`
   (пока заглушка). Наши механизмы правильнее ПРОДОЛЖАТЬ на этих точках, а не строить с нуля.
4. Главный риск — **несовместимость ширины декода**: наш путь по карте включается только при
   `n_tokens == 1` (или `== layer_width`), а сервер батчит несколько запросов в один `llama_decode`.
   Это орто­гональные виды ширины; разбор в разделе 6.
5. Рекомендация по развилке: **libmemex + тонкие типизированные хуки в билдерах ядра** (раздел 3).

## 1. Что даёт даром штатный сервер

Файлы: `examples\server\server.cpp` (2263 стр., HTTP-слой и роутинг), `server-context.cpp`
(5012 стр., слоты/батчинг/декод/KV/сдвиг/кэш), `server-queue.cpp` (очередь задач),
`server-common.cpp`/`server-task.cpp`/`server-chat.cpp`, `common\sampling.cpp` (1175 стр.),
`common\common.h` (дефолты `gpt_params`).

### 1.1 HTTP API и совместимость
Роутинг регистрируется в `server.cpp:~2127-2198` через cpp-httplib (`svr->Get/Post`), обработчики —
лямбды `handle_*`. Сервер **OpenAI-совместим И Anthropic-совместим**, плюс нативный API llama.cpp:

- OpenAI: `/v1/chat/completions` (+ `/chat/completions`) — `handle_chat_completions` (server.cpp:1359);
  `/v1/completions` — `handle_completions_oai` (1282); `/v1/embeddings` — `handle_embeddings_oai` (1584);
  `/v1/models` — `handle_models` (1296); `/v1/responses` — `handle_responses` (1373).
- Anthropic: `/v1/messages` — `handle_anthropic_messages` (1388); `/v1/messages/count_tokens` (1407).
- Нативные: `/completion` (1269), `/infill` (FIM, 1432), `/embedding` (1579), `/tokenize`,
  `/detokenize` (1450/1462), `/apply-template` (1424).
- Служебные: `/health` (726), `/metrics` (Prometheus-текст, 822), `/props` (1027), `/slots` (798),
  `/slots/:id_slot` save/restore/erase (923/953/983), `/version`, `/lora-adapters` горячая
  подмена LoRA (1590/1605), `/control-vectors...` (1639+), SQLite-хранилище сессий
  (`/save`, `/load`, `/sessions`, 1987-2038), CORS-прокси.
- Общее ядро всех completion-обработчиков — `handle_completions_impl` (1093) с дискриминатором
  `oaicompat_type`. Аутентификация по API-ключу (`middleware_validate_api_key`, 630).

### 1.2 Семплеры (`common\sampling.cpp` / `sampling.h`)
Полный современный набор (в харнессе — только argmax). Цепочка по умолчанию (`sampling.h:133-143`):
DRY → top-k → TFS → typical-p → top-p → min-p → XTC → top-n-sigma → температура → adaptive-p.
Конкретно:
- top-k, top-p, min-p, tfs_z, typical_p, температура + **динамическая температура/энтропийная**
  (`llama_sample_entropy`, sampling.cpp:466);
- штрафы repeat/frequency/presence (`llama_sample_repetition_penalties`, 667), плюс отдельный
  penalty-prompt;
- **DRY** (`llama_sample_dry`, 454), **Mirostat v1/v2** (542/545), **XTC** (460),
  **top-n-sigma** (461), **adaptive_p** (ik-специфичный, 479/550);
- **грамматики GBNF** с ленивыми триггерами (`common_grammar`, sampling.h:56; применение
  `llama_grammar_apply`, 527/574/683) и бэкенд **llguidance** (`llama_sampler_init_llg`);
- **CFG / classifier-free guidance** (`llama_sample_apply_guidance`, 631).

### 1.3 Батчинг и слоты
- Слоты = `--parallel N` (`common.h:300`); один слот на последовательность, цикл
  `for (i < n_parallel)` (server-context.cpp:298), контекст слота = `n_ctx / n_parallel` (275).
- **Непрерывный батчинг** (`cont_batching`, default true, common.h:421); планировщик
  `update_slots()` (server-context.cpp:380).
- Один общий `llama_batch` на `max(n_batch, n_parallel)` (server-context.cpp:386). Токены каждого
  слота добавляются со СВОИМ seq_id: `common_batch_add(batch, tok, pos, { slot.id }, logits)`
  (промпт 4148, генерация 3563/3599, черновик спекуляции 3589). Декод — `server_decode` →
  `llama_decode` (2040-2053, вызов из `process_batch_tokens`, 4647-4664), нарезка по `n_batch`
  через `batch_view`.
- Пер-последовательностные операции KV: `llama_kv_cache_seq_cp/rm/add/div`.

### 1.4 Потоковый вывод (SSE)
`handle_completions_impl` (server.cpp:1093), флаг `stream` (1156). Стрим через
`res.set_chunked_content_provider("text/event-stream", ...)` (1265), лямбда
`chunked_content_provider` (1199) тянет результаты `rd->next(...)`, финал — сентинел
`data: [DONE]\n\n` (1251). Куски формата `chat.completion.chunk`.

### 1.5 Продолжение диалога и кэш промптов
- Пер-запросный `cache_prompt` (default true, server-context.cpp:1127).
- **Переиспользование слота по наибольшему префиксу**: сходство нового промпта с `cache_tokens`
  каждого слота (`slot_prompt_similarity`, порог; variant с исключением think-токенов у reasoning-
  моделей), 971-989.
- **RAM-кэш промптов** (`server_prompt_cache`, 400-409) с `prompt_save`/`prompt_load` (462/478).
- **Частичное переиспользование KV** (`llama_model_supports_partial_kv_reuse`, 400).
- Сохранение/восстановление KV слота на диск + SQLite-хранилище сессий.

### 1.6 Сдвиг контекста
- Глобальный `ctx_shift` (default true, common.h:417), авто-отключение для рекуррентных моделей
  (1817), split-графа (1823), отсутствия поддержки (1828).
- Пер-запросные `n_keep`/`n_discard` (1156-1157). Ядро —
  `discard_n_kv_and_cache_tokens(ctx, slot, n_keep, n_discard)` (3308): `llama_kv_cache_seq_rm` +
  `llama_kv_cache_seq_add` (сдвиг позиций на `-kv_discard`), синхронно сдвигает спекулятивный
  контекст. Триггер в цикле генерации (3490-3503).
- Альтернатива — **self-extend / group-attention** (`ga_n`, `ga_w`, `ga_i`).

### 1.7 Спекулятивный декод (важно для раздела 6)
Форк несёт полный спекулятивный/MTP-путь: `speculative.h`, `common_speculative_*`, черновые модели,
ngram, warmup MTP (`server_mtp_warmup`, server-context.cpp:53-75), а также
`server_speculative_requires_single_slot` (79) — то есть машина уже умеет **ширину > 1 внутри одной
последовательности** (верификация черновика) и умеет форсить одиночный слот.

### 1.8 Платформы
cpp-httplib (однофайловый, кроссплатформенный), `CPPHTTPLIB_NO_EXCEPTIONS`. Опциональный TLS
через `httplib::SSLServer` (`CPPHTTPLIB_OPENSSL_SUPPORT`, 501-512), флаги `--ssl-key-file`/`--ssl-cert-file`.
HTTP-слой портируемый (Windows/Linux/macOS); заголовок `Server: ik_llama.cpp`.

## 2. Точки встраивания наших механизмов

### 2.0 Как это устроено в харнессе (шаблон для переноса)
Харнесс уже имеет **единственную точку построения графа**:
`build_any(const ArchModel& am, Graph* g, ..., const BuildOpts& o)` (memex-fwd.cpp:4058),
через которую идут все девять мест харнесса и `Generator::build_one`. `BuildOpts`
(memex-fwd.cpp:3921) несёт все механизмы как необязательные указатели:
`gstat` (GpuStatic), `gx` (GpuExperts), `rs` (ResidentSet), `es` (ExpertStore), `ds` (DeltaState),
`zc` (ZonedKvCache), плюс `min_experts`/`expert_thresh`/`want_hid` и т.д. `ArchModel`
(memex-fwd.cpp:3969) — реестр архитектур с булевыми флагами `can_gstat`/`can_store`/`can_resident`/…,
которые честно отказывают на несовместимых сочетаниях «архитектура × опция».

**Это и есть готовый контракт для ядра**: каждый механизм — опция, а не форк логики.

Подстановки в граф (харнесс) — все локальные и по одной ноде:
- **Голова**: `if (gstat && gstat->head_on()) return gstat->head(c, cur); return ggml_mul_mat(c, out_w, cur);`
  (memex-fwd.cpp:790) — буквально одна строка: `gstat->head()` возвращает тензор той же формы/типа,
  что `ggml_mul_mat(out, x)`, так что ниже по графу ничего не меняется.
- **Слой (внимание+роутер на карте)**: `gstat->layer(c, il, cur, mask)` (2286/2881/3705),
  **под условием `n_tokens == 1`** (2263, 3663) или `n_tokens == gstat->layer_width()` (2872).
- **Резидентные эксперты (расщепление)**: `resident_split_ids(...)` даёт две половины по слотам,
  затем `gx->fork(...)` / `gx->join(...)` вокруг `mul_mat_id` (2511/2550/2560, 3157/3174/3177).
- **Хранилище экспертов в ОЗУ**: `ids = es->slots_node(c, il, sel, gf)` — узел перевода id→slot
  между `top_k` и `mul_mat_id` (3352).

Пооктокенная оркестрация — ручной хостовый клей в цикле генерации харнесса (примерно
memex-fwd.cpp:8100-10013): `set_step` (8549), `upload_kv` (8725)/`upload_delta` (8734),
`observe_prefill` (8796), `observe`+`end_token` (9045-9050, 9820-9822), `sync_slots` (9206/9730),
`take_landed` (9231/9710), `prime`/`slots_node`/`end_token` для ExpertStore (8142, 10013).

Одна строка на архитектуру. | **Чисто.** Форма/тип совпадают. ### 2.3 Размещение тензоров (штатный рычаг `-ot`)
Публичный `llama_model_params.tensor_buft_overrides` (include/llama.h:420); применение в
`llama-load-tensors.cpp`: сбор `overrides` (262-268), синтез `-ncmoe` для
`blk.N.ffn_*_exps` (270-285), единая точка привязки тензора к бэкенду —
`get_context_for_tensor` (460-484, `std::regex_search` по имени). **Это штатный способ положить
«статику на GPU, экспертов на CPU»** без единой строки нашего кода — и именно он проверяется в
фазе 1 (раздел 5).

### 2.4 Архитектурный шов: sched против ручного бэкенда
Харнесс НЕ использует `ggml_backend_sched` — он строит граф на своём `ggml_gallocr` и считает вручную
(`Graph`: `ctx`, `alloc`, `gf`). Ядро сервера считает через `ggml_backend_sched_graph_compute`.
Наши механизмы держат СВОЙ Vulkan-бэкенд (`ggml_backend_vk_init(0)`) и вставляют `ggml_map_custom`-ноды
с `n_tasks=1`, синхронно дёргающие Vulkan изнутри. При встраивании в ядро эти ноды должны остаться на
CPU-бэкенде sched (иначе sched попробует их оффлоадить), а весь тонкий контроль размещения вокруг
256-МиБ BAR-окна карты (вся суть gpu_static/gpu_experts) остаётся ручным. Это выполнимо, но это шов,
который надо держать явным.

## 3. Развилка: опции форка против libmemex

**(а) Встроить механизмы прямо в форк как опции сервера.**
- Плюсы: используем уже существующие точки ядра (`memex_cc`, `defer_experts`, `prefetch_experts`);
  нет отдельной сборки/линковки; один бинарь.
- Минусы: наш код (ручной Vulkan вокруг BAR-окна, `map_custom` в обход sched) размазывается по
  билдерам ядра; форк-форка расходится с апстримом ik_llama; тяжело тестировать в изоляции
  (сейчас у механизмов есть свои selftest'ы `gpu_static_selftest`/`gpu_experts_selftest`, которые
  так потеряются).

**(б) Вынести в `libmemex` и слинковать с сервером.**
- Плюсы: механизмы **уже библиотечной формы** — пространство имён `memex`, чистые заголовки
  (`gpu_static.hpp`, `expert_store.hpp`, `resident_set.hpp`, `gpu_experts.hpp`), зависят только от
  `ggml`/`ggml-backend`, не от харнесса, и несут собственные selftest'ы. Изоляция от churn'а форка;
  тестируемость; ясная граница ответственности.
- Минусы: **всё равно нельзя избежать нескольких хуков в билдерах ядра** — подстановку головы, слоя
  и `slots_node`/`fork`/`join` физически надо скомпилировать внутрь `build_qwen3moe`/`llm_build_moe_ffn`
  и финального matmul. То есть чистой «только линковки» не выйдет.

**Рекомендация: (б) с оговоркой — «libmemex + минимальные типизированные хуки в билдерах ядра».**
Упаковать `memex/*` в libmemex; ввести объект `memex_hooks` в `llm_build_context` (зеркало `BuildOpts`
харнесса), пробросить его в `llm_build_moe_ffn` и в финальную голову; перенести пооктокенную
оркестрацию (`set_step`/`upload_*`/`observe`/`end_token`/`sync_slots`/`take_landed`) в `update_slots`
сервера. Так вся инвазивная Vulkan/sched-обходная логика остаётся в библиотеке (со своими
selftest'ами), а патч ядра сводится к: (1) поле-опция и его проброс, (2) 3-4 точки подстановки
нод, (3) блок оркестрации в одном месте цикла слотов. Реестр `ArchModel` из харнесса переносится
в libmemex как таблица допустимых сочетаний «архитектура × опция», чтобы отказы оставались громкими.

## 4. Что НЕ переносить (и почему)

- **Свой HTTP-сервер / API** — не писать. Форк уже даёт OpenAI + Anthropic + Responses, SSE, слоты,
  непрерывный батчинг, кэш промптов, сдвиг контекста, метрики. Своё — это месяцы работы и заведомо
  хуже (раздел 1).
- **Свой семплер** — не писать. В харнессе только argmax; `common\sampling.cpp` несёт весь
  современный набор + грамматики + llguidance + CFG (1.2). Argmax из харнесса — это просто частный
  случай (temp=0), который сервер уже покрывает.
- **Свой токенизатор** — не писать. `llama-vocab` покрывает все архитектуры (BPE/SPM/…); дубликат
  бессмысленен и опасен рассинхроном спецтокенов.
- **Своё управление KV / сдвиг контекста / продолжение диалога** — не дублировать. Сервер это
  умеет (1.5-1.6). Наш кольцевой/зонный KV — это НЕ замена бухгалтерии KV сервера, а оптимизация
  памяти оконных слоёв ПОД ней; она подключается, не подменяет.
- **Свой цикл спекуляции/MTP** — не писать. Форк уже несёт спекулятивный путь (1.7), и наш
  `layer_width>1` естественно ложится именно на него (раздел 6), а не на отдельную машину.

## 5. План по фазам (с оценкой в неделях)

Оценки — грубые, для одного разработчика, на текущем железе (RX 6500 XT, Windows 11).

### Фаза 1 — прототип-шлюз на mx1 (1-2 недели)
Собрать штатный `llama-server` из форка. Запустить mx1 с НАТИВНЫМ `-ot exps=CPU`
(статика → GPU-бэкенд, эксперты → CPU) и убедиться, что внутри сервера воспроизводится эталонная
скорость харнесса (порядка **~19 ток/с**). **Если не воспроизводится — интеграция неверна, дальше
не идти.** Побочно этот замер отвечает на важный вопрос: если нативный `-ot` уже даёт число, то часть
`GpuStatic` избыточна на бэкендах, где GPU-путь работает; если НЕ даёт (ловушка BAR-окна 256 МиБ на
этой карте — ровно то, ради чего `GpuStatic` руками управляет размещением), то ручная раскладка
`GpuStatic` несущая. Развилка честно фиксируется здесь.
Усилия: сборка + прогон + сверка. Риск низкий.

### Фаза 2 — статика на карте как опция сервера (2-3 недели)
Упаковать libmemex; ввести `memex_hooks` в `llm_build_context`. Подставить **голову** (одна строка,
аналог memex-fwd.cpp:790) и — под флагом и только при `n_parallel == 1` — **путь слоя** `gstat->layer()`.
Перенести `set_step`/`upload_kv`/`upload_delta` в `update_slots`. Прибить наши `map_custom`-ноды к
CPU-бэкенду в sched (риск 2.4). Шлюз: побитово совпадающие логиты против CPU-графа + скорость не хуже
харнесса. Риск средний (шов sched + BAR-раскладка).

### Фаза 3 — хранилище экспертов, ярус ОЗУ (3-4 недели)
Вместо собственного `ExpertStore` с чтением по файловым смещениям — **переиспользовать ядрёные**
`defer_experts` + `expert_tensor_index` + `drop_mmap_expert_pages`, снимая двойную память (дефект
трэшинга 88fd390). Резидентность гнать через `slots_node` в `llm_build_moe_ffn`. Явно закрыть
Windows-портируемость отложенного пути (сейчас Linux-only, llama.cpp:5112 / llama-mmap.cpp:65) —
это отдельная подзадача. Шлюз: доля попаданий + отсутствие трэшинга. Риск средний-высокий (портируемость).

### Фаза 4 — резидентные эксперты на карте (3-4 недели)
`fork`/`join` в точках `mul_mat_id`, маска резидентности как вход. Требует рабочего Vulkan-потока и
**сериализации на уровне процесса**: GpuStatic и GpuExperts не делят один `vk_device` (gpu_static.hpp:60).
Практически это значит: либо статика-слой, либо резидентные эксперты — не оба сразу; выбор — параметр
запуска сервера. Шлюз: `gpu_experts_selftest` внутри процесса + сверка `--check`. Риск высокий.

### Фаза 5 — предсказатель R1 как префетчер (2-3 недели)
Снять скрытое состояние (`hid_outs`/`want_hid`) внутри процесса, поднять микромодель R1 (сейчас
только в `bench/train_r1.py`), гнать префетч через существующий `cparams.prefetch_experts`
(заглушка, llama-cparams.h:42). Шлюз: снижение синхронных промахов против чистой частоты
(эталон — `bench/route_lab.py`, +6..11 пунктов). Риск средний (новый код, но точка подключения есть).

**Итого**: полный путь ≈ 11-16 недель. Ценное ядро продукта (сервер + статика на карте, фазы 1-2)
≈ **4-5 недель**.

## 6. Совместимость декода одного токена (ГЛАВНЫЙ РИСК)

**Суть коллизии.** Наш путь по карте заточен под `ne[1] == 1`: слой карты строится для ширины 1
(или заданного `layer_width`), а Vulkan падал при ширине > 1 (перестановки становятся реальными —
gpu_static.hpp:148-156; «ловушка 7.6»). Условие включения в графе — жёсткое: `n_tokens == 1`
(memex-fwd.cpp:2263, 3663) либо `n_tokens == gstat->layer_width()` (2872).

Сервер же батчит **по запросам**: один `llama_batch` набивается токенами из разных слотов, по одному
на слот, каждый со своим seq_id (`common_batch_add(batch, tok, pos, { slot.id }, ...)`,
server-context.cpp:3563). При мультипользовательской генерации `batch.n_tokens` = число активных слотов
> 1. Внутри ubatch ширина = `n_ubatch` (llama.cpp:6352), а в `llm_build_moe_ffn` форма выбора —
`[n_expert_used, n_tokens]` (llama-build-context.cpp:1683).

**Ключевое различие двух «ширин».** Есть два ортогональных вида ширины > 1:
1. **Ширина по запросам** (батчинг разных последовательностей в один decode) — то, что делает сервер.
   Это N НЕЗАВИСИМЫХ задач ширины 1, а не одна задача ширины N. Наш путь по карте держит ОДИН
   KV-буфер и одно перенос­имое состояние (`upload_kv` — один кэш на промпт), то есть неявно
   предполагает одну последовательность.
2. **Ширина внутри одной последовательности** (MTP / верификация спекулятивного черновика) — это
   `layer_width` из `GpuStatic` (gpu_static.hpp:156). ЕЁ карта умеет: прогон на K токенов одной
   последовательности измерен и даёт ~18 ток/с (bench/spec_width.ps1).

То есть карта совместима с (2) и НЕ совместима с (1) в общем виде.

**Как уживить — три варианта, по возрастанию сложности:**

- **A. Гейт по одиночному слоту (рекомендация для фаз 2-4).** Включать путь карты только когда
  активна одна последовательность (`n_parallel == 1`, или динамически — когда занят ровно один слот).
  На батче из нескольких слотов откатываться на штатный CPU-граф. Это ровно текущий инвариант
  харнесса, ничего нового доказывать не надо; корректность бесплатна. У сервера уже есть прецедент
  форса одиночного слота — `server_speculative_requires_single_slot` (server-context.cpp:79).
  Минус: при многих пользователях карта простаивает.

- **B. Пер-слотовая итерация графа карты.** На батче из N слот-токенов вызывать граф карты N раз
  (N синхронных диспатчей, каждый — своя ширина-1 задача со своим KV). Работает при мультислоте, но
  платит N пересечений CPU↔GPU за токен (177 мкс каждое, gpu_static.hpp:24-26) и требует
  пер-слотового KV на устройстве. Оправдано только если N мало и карта всё равно быстрее CPU.

- **C. Настоящие Vulkan-графы ширины N.** То, что `GpuStatic::layer_width` уже начал для MTP
  (gpu_static.hpp:150-156), но это ширина ОДНОЙ последовательности (спекуляция), а не разные
  последовательности батча. Свести «батч по запросам» к одному графу ширины N нельзя без общей маски
  и общего KV, которых у разных последовательностей нет. Практически бесперспективно для (1);
  осмысленно только чтобы сомкнуться со спекулятивным путём сервера (2).

**Дополнительный фактор — batch-shared эксперты в ядре.** В `llm_build_moe_ffn` уже есть ветка
`memex_shared_experts_enabled() && n_tokens > 1` (llama-build-context.cpp:1653): при ширине > 1
делается ОДИН общий top-k на батч. Любой наш предсказатель/резидентность должен учитывать этот
случай, иначе на ширине > 1 он будет расходиться с прочитанным ядром выбором.

**Вывод по риску.** Правильная развязка — не пытаться сделать карту «шире», а **развести две ширины**:
путь карты обслуживает одиночную последовательность (вариант A) и, отдельно, смыкается со
спекулятивным `layer_width` сервера (вариант 2). Мультипользовательский батчинг обслуживается
штатным CPU/GPU-графом ядра. Это сохраняет и корректность (побитовость), и почти всю выгоду карты
(одиночный интерактивный сеанс — основной сценарий), ценой того, что карта не ускоряет одновременный
мультипользовательский поток. Попытка сделать иначе (вариант C для случая 1) — это переписывание
верифицированного пути и повторный риск падения Vulkan при ширине > 1.
