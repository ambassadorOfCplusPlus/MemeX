# Каталог методов: что применено, что опровергнуто, что в очереди

Реестр приёмов ускорения MoE-инференса на слабом железе. Для каждого — что он делает,
и главное: **какое у нас измерение**. Метод без числа рядом считается непроверенным,
даже если он опубликован и звучит убедительно.

Железо, к которому всё привязано (измерено, не из спецификаций): i3-10100F 4 ядра,
RAM 31.9 ГБ на 21.5 ГБ/с в четыре потока, RX 6500 XT с 3.4 ГБ свободной VRAM на
84.6 ГБ/с при одном токене, PCIe 3.0 x4 = 3.94 ГБ/с, SSD 232 МБ/с и HDD 62 МБ/с на
случайном чтении по 1.29 МБ.

## Применено и измерено

| Метод | Что делает | Наш результат |
|---|---|---|
| **Спекулятивное декодирование** (черновик того же семейства) | несколько токенов за одно чтение весов | 6.16 → **8.40 ток/с**, черновик 0.6B на GPU, глубина 5 |
| **ik_llama.cpp** | быстрые CPU-ядра для MoE | **8.85 ток/с** на тех же весах и флагах |
| **Отключение flash-attention на CPU** | у ik/llama.cpp на CPU `-fa` вредит | при 8192 контекста 1.14 → **3.30 ток/с** |
| **Пер-экспертная точность** (наш блоб) | каждый эксперт в своей битности | 30.5 ГБ блоб, слой считается за **1.245 мс** против 1.324 у исходной точности |
| **Небуферизованное чтение** фоновых загрузок | не вытеснять модель из файлового кэша | 4.69 → **8.33 ток/с** при активной фоновой подкачке |
| **Лестница битности** (водоналивное распределение) | бит тем, кто чаще нужен | ущерб **в 1.35 раза меньше** при равной памяти против двух уровней |
| **Двойная буферизация при смене точности** | новая копия пишется рядом, старая обслуживает | остановок ноль, лишней памяти 187 МБ |
| **Избыточная копия** (EPLB redundant experts) | грубая копия живёт рядом с точной | понижение точности стало мгновенным, без чтения с диска |
| **Окно статистики + перебалансировка** (EPLB window/step) | решения по накопленной нагрузке | напрасные сбросы с 100% до 32% |
| **Прогрев на префилле** | набор строится по маршрутам самого промпта | набор по первым 128 токенам закрывает **91%** от предела (проза); в движке даёт 24 повышения до первого сгенерированного токена |
| **Замкнутая петля** (политика + загрузчик + вычисление + выбор) | всё вместе на одном пути | при бюджете 24 из 128: полная точность у 36.9% обращений без бонуса и **52.4%** с бонусом 0.10; понижения все мгновенные; генерация не ждёт |
| **Одновременный счёт CPU+GPU** | резидентные в VRAM считает GPU, остальных CPU, параллельно | перекрытие **86%**, экспертный FFN 19.20 → **27.70 ток/с** (x1.44). Топ-16 экспертов на слой влезают в 3.19 ГБ и закрывают 50.9% спроса |
| **Гибридный шаг: горячие эксперты на карте, холодные на процессоре** | резидентные считаются отдельными матвекторами в VRAM асинхронно, холодные одновременно на процессоре, синхронизация раз в слой, набор обновляется раз в 3 токена с бюджетом перемещений и отложенной активацией | корректность **12 из 12 токенов** без бонуса; внутри нашего движка **×1.40** (6.55 → 9.14 ток/с) при бонусе 0.10 и резидентности 42.2%. Без бонуса выходит в ноль: карта берёт 2 эксперта из 8, экономит 0.26 мс на слой, пересечение границы стоит 0.12 |
| **KV зонами** (стоки, блокнот, сжатый хвост, окно) | хвост рангом 128, остальное точно | чтение при 32k: 3.22 → **0.85 ГБ** на токен (в 3.80 раза), потолок 6.24 → 23.70 ток/с на CPU и 99.76 на GPU |
| **Квантованный хвост KV** (Q8_0, полный ранг) | хвост зон в родном блочном формате ggml вместо низкого ранга | ошибка выхода внимания **2.58%** против 70.6% у ранга 128 при том же объёме; заполнение 32k позиций 554 мс против 1245 |
| **Поворот Адамара в хвосте** (QuaRot) | ключи поворачиваются перед квантованием, запрос — вместе с ними | ошибка хвоста 3.09 → **1.57%**, зонной памяти целиком 2.92 → **1.53%**; поворот значений бесполезен (1.58 против 1.57) — у них блоки по позициям |
| **Cache-conditional routing** (SMoE dynamic expert caching) | бонус к оценке резидентных экспертов при отборе top-k | бонус 0.10: попадания 67.3 → **79.1%** (−36% промахов) ценой **+0.73% перплексии** (8.727 → 8.791). Бонус 0.20: 86.1% попаданий, но +3.67% — невыгодно. Реализовано в форке (`MEMEX_CACHE_BONUS`, `MEMEX_RESIDENT_FILE`) |

## Опровергнуто нашими же замерами

| **LExI — своё число экспертов по слоям** | Роутер плоский **равномерно**, а не в среднем, поэтому послойной версии нечего эксплуатировать. Из трассы полных распределений (`memex/lexi_plan.py`, 48 слоёв): доля массы в top-1 около 0.22, в top-7 около 0.92 в каждом слое, разброс между слоями всего 0.908…0.926. Водоналивной план при бюджете 2% средней потери массы отбрасывает восьмого эксперта лишь в 14 слоях из 48 — 370 экспертов вместо 384, экономия **3.6%**. Замеров на модели не потребовалось |
| **Сокращение числа экспертов** (`-ser`, оно же SER) | У плоского роутера нет бесплатной зоны. Замер сильнейшим из возможных тестов — совпадением сгенерированного текста с эталоном, 24 токена: относительный порог 0.30 при минимуме 4 даёт **24 из 24**, то есть не отбрасывает вообще ничего, а 0.35 даёт **0 из 24**. Обрыв объясняется трассой: верхний эксперт несёт 22.7% веса, восьмой 7.6%, то есть 0.33 от верхнего — эксперты с пятого по восьмой сидят кучей около порога, и он либо не задевает никого, либо срезает сразу половину. Ядро `mul_mat_id` поддержку `-1` имеет и байты действительно не читает; проблема не в реализации, а в распределении. Кстати, ровно поэтому вызов и был закомментирован в форке |
| **Безмодельная спекуляция** (все варианты форка) | На нашей задаче черновики почти не принимаются, а построение их стоит. Замер на промпте с повторами, 96 токенов, база 6.29 ток/с: `ngram-simple` 6.80 при **нуле** порождённых черновиков (то есть прирост — шум), `ngram-map-k` 6.72 тоже при нуле, `suffix` 6.13 при нуле и 110 мс на вызов построения автомата, `ngram-mod` 5.58 (три черновика, принято ноль), `ngram-cache` **4.69** — двенадцать черновиков, принято 3 токена из 84 и по 47 мс на вызов. Живой остаётся только спекуляция настоящим черновиком: в mainline она давала 6.16 → 8.40 |

| **Предсказание экспертов на 2 токена вперёд** | идеальный прогноз даёт +2.5 пункта попаданий, канал всё равно узкое место |

| **Перепаковка `-rtr` на генерации** | −12% скорости (но +25% на префилле, поэтому включать по режиму) |

Работает на моделях с «пиковым» роутером, у этой лосс балансировки и нормировка top-k специально выравнивают вклады |

## В очереди, с оценкой

| **LExI** | адаптивное число активных экспертов **по слоям**, без данных, только по весам | наш отказ от Adaptive-K касался выбора внутри токена (роутер плоский); выбор по слоям не опровергнут | оценить важность слоёв по весам, померить перплексию |
| **SERE** | перенаправление токена от второстепенного эксперта к похожему основному | складывается с cache-conditional: перенаправлять к похожему **и резидентному** | мера сходства экспертов |

| Метод | Идея | Почему стоит | Чего требует |
|---|---|---|---|
| **PuzzleMoE** | сжатие **между** экспертами: поэлементная избыточность, двойная маска (общая часть + специфичная), упаковка по битам | +16.7% MMLU против прежних методов при сжатии вдвое, ×1.80 пропускной. Ортогонально нашей лестнице — мы жмём внутри эксперта. Наш прежний отказ от факторизации касался низкоранговой аппроксимации, здесь механизм другой | прочитать статью, проверить на одном слое |
| **FloE** | избыточность внутри матриц редко активируемых экспертов, сжатие на лету | та же семья, что PuzzleMoE, но внутри эксперта | прочитать |
| **ReMoE** | дообучение роутера на локальность | перекрытие соседних токенов +26–27% (у нас 33.9% → ~43%) | обучение роутера (12M параметров — по силам) |
| **CasMoE** | предсказание паттернов всех слоёв по офлайн-трассам | prefetch внутри токена | трассы есть, нужен предсказатель |
| **Pre-gated MoE** | роутер слоя i предсказывает слой i+1 | перенос перекрывается счётом текущего слоя | правка графа, лёгкое дообучение |
| **Одновременный счёт CPU+GPU** | горячие на GPU, холодные на CPU, параллельно | перекрытие измерено 94–109%, проекция ×1.6…1.95 | разрез оператора MoE на две ветви |
| **Калиброванное квантование** (GPTQ/AWQ) | компенсировать ошибку по активациям | наш Q4_K дал +2.5% перплексии; калибровка даст меньше | калибровочный проход |

## Прочитано, но пока без нашей оценки

* **MoBiLE** — большие и маленькие эксперты вместе, plug-and-play для потребительских GPU.
* **FineMoE** (EuroSys'26) — асинхронный prefetch издатель-подписчик: −47% задержки, +39% попаданий.
* **ADEPT** — двухстадийная выгрузка, >80% попаданий, 3.45× к наивной подкачке.
* **DraftExpert** — черновик даёт будущие токены, по ним прогоняются роутеры большой модели.
* **PowerInfer** — горячие нейроны на GPU, холодные на CPU; наш аналог для экспертов.
* **MxMoE / MoPEQ / DyMoE** — смешанная точность по частоте активации и чувствительности.
* **SlimCaching**, **SiftMoE**, **Q-Infer**, **HybriMoE**, **Klotski**, **HOBBIT** — семейство
  «кэш экспертов + гибридное расписание CPU/GPU».
* **HAP** (hybrid adaptive parallelism) — разделяет модель на модуль внимания и модуль
  экспертов, каждому своя модель задержки, стратегия параллелизма выбирается отдельно;
  1.57–1.77× против тензорного параллелизма. Машинерия для многих GPU нам не подходит,
  но **вывод совпал с нашим измерением**: внимание и эксперты требуют разных решений о
  размещении (у нас внимание при 32k: 162 мс на CPU против 38 на GPU).
* **DAOP** — считает сразу предсказанными экспертами без проверки, то есть меняет
  качество на задержку. У нас плохая сделка: идеальное предсказание даёт +2.5 пункта
  попаданий, а узкое место — канал, не знание.
* **LLMKube**, флаг `--cpu-moe` в llama.cpp — эквивалент нашего `-ncmoe`. Рядом нашлось
  обсуждение llama.cpp №24528: «кэш экспертов, кэширование горячих CPU-резидентных
  экспертов в VRAM с гибридным исполнением по попаданию/промаху» — буквально наша схема,
  и у нас есть измерения, которых там нет.
* **ResMoE** — не найдено; поиск выдаёт ReMoE (дообучение роутера), это другое.
* **KTransformers** (SOSP'25, Tsinghua) — «полный потенциал гибридного CPU/GPU инференса
  для MoE». Ближайшая к нам существующая система: тот же сценарий слабой карты и
  процессора. Изучить внимательно, а не по аннотации.
* **Context-Aware MoE on CXL-enabled GPU-NDP** — динамическое размещение экспертов по
  статистике маршрутизации **плюс** динамический выбор битности. Независимое повторение
  двух наших главных идей в другой аппаратной среде.
* **MODE** — пер-экспертная смешанная точность для мультимодальных MoE.
* **MoE-SpAc** — спекулятивная полезность активации на гетерогенном edge.
* **MoE-Inference-Bench** — набор для систематического сравнения оптимизаций MoE.
* **Патенты CN122086631A и CN122261771A** — по этим номерам поиск ничего не дал; либо
  номера неточные, либо заявки не проиндексированы. Смежное найденное описано выше.

## Правила измерения, добытые дорого

1. **Проверять файл по хешу до любых замеров.** Недокачанный файл с точным размером
   загружается, считает и выдаёт мусор; один такой стоил вечера бенчмарков.
2. **Останавливать загрузки на время замера** (`tools/bench_guard.sh`). Восемь потоков
   докачки на четырёх ядрах превратили 1.4 мс в 888 мс и породили ложную теорию.
3. **Мерить серией и брать медиану.** Один замер не отличает изменение от чужого
   процесса: одинаковый код давал от 1.6 до 102 мс.
4. **Рабочий набор должен не влезать в кэш.** На 11 МБ проба дала GPU 36 ГБ/с и CPU
   30.6; на 1.6 ГБ — 84.6 и 20.1, и второе совпало с независимым замером полосы.
5. **Сверять расчёт с замером.** Каждый раз, когда они расходились больше чем в два
   раза, виноват был стенд, а не железо.
6. **Один замер может убить один метод и оправдать другой.** Плоское распределение веса
   роутера (8-й эксперт 7.6% против 22.7% у первого) сделало Adaptive-K бесполезным и
   ровно этим же сделало подмену резидентным эксперта почти бесплатной.
7. **Отбрасывать последний слой при разборе трасс.** llama.cpp считает его FFN только
   для последнего токена, и он трижды обрезал нам статистику до одного-двух токенов.
8. **Подогнанный базис проверять на тех же векторах, что хранит рантайм.** Трассировщик
   писал ключи слоя четыре раза, включая копию до нормировки с нормой строки 80.6 против
   2.0. Ковариация взвешивает квадратом нормы, поэтому копия несла в 1600 раз больше
   энергии и базис подгонялся под неё: 13.11% ошибки на смеси и 40.66% на настоящих
   ключах. Поймало это только сравнение Python и C++ на одном файле базиса — совпадение
   двух независимых реализаций стоит дороже, чем правдоподобная цифра из одной.
9. **Сверять имена узлов точно, а не по префиксу.** `strncmp(name, "Kcur", 4)` ловит
   `Kcur`, `Kcur_normed` и все переформатирования: один граф Qwen3 даёт четыре записи там,
   где нужна одна.
10. **Сверять граф с простым счётом на хосте прежде, чем брать из него хоть одну цифру
    качества.** Зонный граф расходился с точным на девять порядков при базисе полного
    ранга, и по коду это было не видно; независимый счёт той же формулы на хосте за десять
    минут показал, что алгебра верна, а виновата ggml-запись.
11. **Функция сравнения не должна возвращать «совпало» при нулевом эталоне.** Точный граф
    выдавал нули, знаменатель был нулём, и `den > 0 ? … : 0.0` объявляла идеальное
    совпадение. Тест с пустым хвостом «сошёлся» ровно потому, что оба ответа были нулевыми.
    Теперь при нулевом эталоне возвращается −1, и рядом всегда печатаются нормы.
12. **Ядра форка требуют кратности четырём по длине свёртки, и молча врут иначе.** Контекст
    2780 сходится с хостом до 0.001%, 2777–2779 расходятся больше чем на 100%. Выравнивать
    длину зон (до 32, как llama.cpp) и маскировать добивку через `-inf`.
13. **Экономию, мотивированную полосой, нельзя мерить на контексте, влезающем в кэш.** При
    2777 позициях KV весит 5.69 МБ, целиком лежит в L3, и 2.46× меньшего чтения дали 1.12×
    по времени. Это не опровержение идеи, а замер не в том режиме.
14. **Подогнанный базис проверять на отложенном тексте.** Базис на английской беллетристике
    оставляет 9.14% на своих ключах и 29.95% на C++; на значениях 21.41% против 76.61%.
    Смесь доменов почти не проигрывает доменному базису (15.72% против 14.13% на коде) и
    переносится, а подгонка на самом контексте проигрывает смеси: базис по первой половине
    даёт на второй 20.73% против 11.84%, и причина в размере выборки, а не в дрейфе.
15. **Сравнение обязано отказываться при разных размерах.** llama.cpp обрезает последний
    слой до выходных токенов, и сличение по пересечению поставило наш нулевой токен против их
    последнего — 209% расхождения, которого не было. Эта обрезка подвела проект четыре раза.
16. **Прежде чем искать ошибку в своём коде, проверь точность эталона.** Пять процентов
    расхождения на логитах объяснились тем, что эталон держит KV в f16, а мы в f32 — то есть
    расходились не потому, что мы неправы, а потому что мы точнее.
17. **Сверять по именам узлов эталона, за одну загрузку.** Модель грузится две минуты, поэтому
    просить по одному тензору за прогон превращает бинарный поиск в час; ловить все нужные
    узлы сразу стоит 160 КБ на слой.
18. **Сверять флаги сборки, прежде чем сравнивать устройства.** Дерево `build-vk`, которым
    делались все замеры с картой, было сконфигурировано с `GGML_FMA=OFF` и без `F16C`, тогда
    как обычное дерево имеет оба. То есть процессорный путь в сборке с картой был искалечен, и
    любое сравнение «карта против процессора» из него переоценивало карту. Видно это стало
    только когда одна и та же конфигурация `-ngl 0` дала 10.11 ток/с в одном дереве и 13.21 в
    другом.
19. **Перепаковка весов (`-rtr`) на чисто процессорной машине — бесплатные проценты.** +17% на
    генерации (7.99 → 9.33 на Q6) и почти вдвое на префилле. Мы её просто не включали.
20. **Гиперпоточность здесь вредит.** Восемь потоков против четырёх: 12.17 против 12.82 с
    перепаковкой. Четыре физических ядра — четыре потока.
21. **Совпадение токенов — хрупкий критерий, если реализации отличаются порядком
    суммирования.** Гибридный движок при 0 резидентных слотов совпал с эталоном на 1 токене
    из 12, при 24 слотах — на 12 из 12, и это выглядело как поломка холодной ветви. Печать
    зазора между лучшим и вторым логитом закрыла вопрос: первое решение в обоих прогонах
    совпадает до пятого знака, а на втором зазор **0.026 при величине 25**, то есть одна
    тысячная. Жадная выборка превращает такую почти-ничью в подбрасывание монеты, и
    монотонность «больше экспертов на карте — больше совпадений» оказалась удачей, а не
    качеством. Для реализации, которая складывает доли слоя на хосте, а не внутри одного
    графа, правильный критерий — логиты или перплексия; совпадение текста годится только для
    побитово одинаковой арифметики.
22. **Две реализации одного и того же надо сличать между собой, а не только с эталоном.**
    Батчевый `mul_mat_id` и поштучные матвекторы на холодной ветви совпали до 0.0000% — это и
    снимало подозрение с батчевой формы, пока зазор логитов не объяснил остальное.
23. **Убедись, что база приготовлена не лучше кандидата.** «Цена четырёх бит» вышла +7.9%
    перплексии, но исходный файл был сделан **с матрицей важности**, а мой переквант — без, и
    типы `IQ*` спроектированы именно под неё. Плюс переквантование уже квантованного (Q6 → IQ4)
    складывает две ошибки. Подпись ошибки видна отдельно: вариант с внимания в Q6 и `down` в
    5.25 бита дал 2.2677 против 2.2918 — разница 0.024 при погрешности 0.06, то есть
    неразличимо, при 24% потере скорости. Когда перераспределение битов не меняет ничего, дело
    не в битах.
24. **Само наличие неиспользуемого бэкенда стоит денег.** Сборка с Vulkan даёт 10.23 ток/с
    против 13.55 у обычной на той же конфигурации: модель кладётся в host-visible память карты,
    а процессор читает её медленнее. Если карта не окупается — её сборку запускать нельзя.

## Правило 25. `to_float` на целом слое врёт для типов со строчными метаданными

В этом форке у `ggml_type_traits_t` есть поле `row_meta_size`, и у `IQ4_KS` оно равно 4: каждая
строка несёт впереди свой масштаб типа float. Один вызов `to_float` на весь многострочный блок
раскодирует нулевую строку верно, а масштабы остальных примет за данные — и выдаст правдоподобную
чепуху (замерено: 117-137% ошибки там, где её 7.5%). Для любого типа с `row_meta_size > 0`
вызывать построчно. Проверять этим же способом каждый новый инструмент: сверять его вывод на
q6_K, q4_K и iq4_xs, где ответ известен.

## Правило 26. Частота использования не входит в критерий распределения битов

Для любой сущности, выбираемой с частотой f: вклад в ошибку ~ f·e, вклад в байты ~ f·s, и в
отношении выигрыша к цене f сокращается. Поэтому «дадим больше бит тому, что чаще используется»
— неверно; решает только то, насколько подъём точности уменьшает ошибку именно этой сущности.
Проверено на экспертах MoE: ошибка плоская, ветка закрыта (см. ARCHITECTURE §8.30).

## Правило 27. Прежде чем повторять чужой рецепт, посмотреть, что в исходном файле уже сделано

Файл unsloth `UD-Q6_K_XL` хранит блоки 0 и 47 в q8_0, а остальные в q6_K — защита первого и
последнего слоя. Наши профили переквантования обрабатывали все 48 блоков одинаково и эту защиту
снимали, ни разу этого не заметив. Неоднородность исходника надо читать до того, как назначать
свою раскладку: она уже содержит чей-то измеренный вывод.

## Правило 28. `ggml_get_rows` по перепакованному тензору даёт тихо неверный результат

`-rtr` / `repack_tensors` меняет только `tensor->type`, оставляя `ne`/`nb` и размер строки теми
же, поэтому все построенные виды остаются в силе, а `mul_mat`/`mul_mat_id` работают через
`iqk_mul_mat` — для этого перепаковка и существует. Но `ggml_get_rows` идёт по обобщённому
квантованному пути (`ggml.c:19562`) и вызывает `to_float` построчно, тогда как
`dequantize_row_q6_k_r4` (`iqk_quantize.cpp:6229`) раскодирует **четыре переплетённые строки
сразу**. Ни утверждения, ни падения — просто другие числа.

Спасает только то, что `is_forbidden_tensor` (`iqk_quantize.cpp:8448`) исключает
`token_embd.weight` из перепаковки, а единственный `get_rows` по весам в наших графах — это
поиск эмбеддинга. Если появится второй, он будет молча неверным.

## Правило 29. Типы со строчными метаданными: полный список

`row_meta_size > 0` у двадцати типов, а не у одного. Среди них те, что мы используем или можем
включить: **IQ4_KS (4), IQ5_KS (4), IQ4_KSS (4), IQ3_KS (2), IQ2_KS (2), IQ2_KL (2)** и
перепакованные **IQ4_KS_R4 (4), IQ5_KS_R4 (4)**; далее IQ1_S_R4, IQ1_M_R4, IQ1_BN (2), IQ2_BN,
IQ2_BN_R4 (4), Q8_KV (8), Q8_KV_R8 (4), Q8_K16 (20), IQ1_KT, IQ2_KT, IQ3_KT, IQ4_KT (4).
Нуль у всех наследственных: F32, F16, Q4_0, Q4_1, Q5_0, Q5_1, Q8_0, Q8_1, I2_S.

Сам квантователь безопасен: при `row_meta_size > 0` он отводит тензор на построчную ветку
(`llama-quantize.cpp:148`). Опасны только наши собственные обходы данных.

## Правило 30. `fseek` с приведением к `long` под MSVC переполняется на 2 ГБ

`long` здесь 32-битный. Нужен `_fseeki64` / `_ftelli64`. Найдено латентно в
`memex-attn.cpp:105`, `memex-router.cpp:52`, `memex-run.cpp:74`, `cpp/src/blob_loader.cpp:146`.
Правильный образец — `memex-qerr.cpp:206`.

## Правило 31. Различать бюджет скорости и бюджет размера

Байты за токен взвешены частотой использования, размер файла — нет. Поэтому при подъёме точности
частота сокращается в бюджете скорости и не сокращается в бюджете размера. Один и тот же план
может быть выигрышным в одном и проигрышным в другом, и говорить «этот план лучше» без указания
бюджета — бессмысленно. Проверено: градация битов по частоте экспертов дороже однородного подъёма
по байтам за токен и дешевле его по размеру файла.

## Правило 32. Прежде чем урезать что-то как «неиспользуемое», проверить на другом распределении входа

Маршрутизация в MoE зависит от входа. Набор редких экспертов, снятый на одном виде текста, не
обязан совпадать с набором на другом, а измерять качество мы склонны на том же виде текста, на
котором строили план — то есть ровно там, где ущерб не проявится. Правильная проверка: взять
набор, определённый на распределении A, и посмотреть, какая доля выборов попадает в него на
распределении B.

## Правило 33. Проверять на распределении, где ущерб проявится, а не там, где строился план

Правило 32 сработало с первого применения и заслуживает усиления. Набор «редких экспертов», снятый
на коде, на русском забирает 24.1% выборов против 25.0% у случайного набора — то есть не несёт
информации о редкости вообще. Плата выросла с оценённых +1.5% до 8-12%, и главное: наша проверка
перплексии на коде этого не увидела бы **по построению**.

Общий вид: если приём настраивается по данным распределения A, измерять его надо на B, где он
может сломаться. Совпадение метрики на A — не подтверждение, а тавтология.

И обязательное плечо-контроль: отложенная выборка из **того же** распределения A. Без неё нельзя
отличить сдвиг распределения от шума выборки. Здесь оно дало 0.786 при пороге 0.834 и сделало всю
таблицу читаемой.

## Правило 34. Считать байты до объявления вывода, и проверять оценку на физическую возможность

Дважды за один день вывод строился на несчитанном бюджете: сначала «28% времени не память» (из
оценки 1.29 ГБ вместо настоящих 1.804), потом «Coder-Next — путь к 20» (без расчёта его 2.2 ГБ).
Обе ошибки ловятся одной проверкой: **разделить оценку байт на число активных параметров и
сравнить с самым грубым типом в файле.** 1.29 ГБ по 3.042 млрд даёт 3.39 бита на вес — ниже
iq4_xs, то есть невозможно.

## Правило 35. Один прогон не отличает 5% от нуля

Четыре повтора одной конфигурации: CV 4.2%, разброс 9.9%. Значит любое утверждение о выигрыше
меньше ~5% требует повторов. Проверено на собственных прошлых выводах: «4 потока лучше 8» стояло
на разнице 5.3% и оказалось неверным — при повторах t=8 быстрее на 7%.

## Правило 36. Отрицательный замер закрывает конфигурацию, а не механизм

Чтобы закрыть механизм, нужно объяснение, проверенное **отдельно** от самого замера. Выгрузка
слоёв на карту дала ×0.15, и объяснение «`mul_mat_id` недоступен» было правдоподобным и
непроверенным. На деле он доступен, а не реализованы типы `IQ4_KS` и `_R4` — то есть замер был
верен, а вывод из него шире, чем позволяли данные. Направление простояло закрытым неделю.

Проверка: если объяснение отказа нельзя подтвердить независимым измерением, вывод формулируется
как «в этой конфигурации», а не «на этом железе».

## Правило 37. Мелкие передачи считать по задержке, крупные по полосе

16 КБ туда-обратно через PCIe стоят 177 мкс независимо от размера — это задержка, а не полоса.
Расчёт по полосе дал 0.2 мс там, где на самом деле 8.5 мс. Порог примерно там, где размер,
делённый на полосу, сравнивается с задержкой одного обмена: ниже него считать надо по числу
обменов, а не по объёму.

## Правило 38. Проверять, что бинарник запускается, а не что файл существует

`ggml.dll` исчезла из каталога сборки, CMake считал цель готовой, обычная пересборка была
пустышкой, а все прогоны падали с `STATUS_DLL_NOT_FOUND` (код -1073741515) **без сообщения** — в
логе оставались одни «не запустилось» без причины. `Test-Path` этого не ловит. Лечится
`--clean-first` для ggml и проверкой `--version` перед каждой фазой.

## Правило 39. Разделение вычисления переставляет порядок сложений, и токены этого не покажут

Разделив вклады восьми экспертов на две половины и сложив итоги половин, получаем другой порядок
сложения чисел с плавающей точкой. Ошибка компаундится по слоям: ноль на слое 0, **2.5e-8 на
слое 1**, 0.11% к слою 16, **1.6% к слою 47**, и 3-6% относительной L2 на логитах — при том что
сгенерированные токены **совпадали**. То есть проверка «24 из 24 совпало» этого класса ошибок не
ловит вовсе.

Лечение: складывать половины **послотно**, до умножения на веса маршрутизации и до свёртки. Тогда
это буквально те же восемь сложений в том же порядке, и расхождение равно нулю до последнего
разряда.

Проверять любое разделение вычисления надо послойно и по логитам, а не по выходным токенам. И то
же требование переносится на разделение между устройствами: половина, посчитанная на карте, должна
складываться с процессорной послотно.

## 40. Ownership and silence are two different questions, and a mixed queue needs both

The machine lock was introduced because four successive resource checks each caught the previous
collision and missed the next. It was correct and it was still not enough: a lock only binds the
scripts that call it, and three scripts in this queue predate it. One of them was midway through a
measurement, holding 12.6 GB, when a lock-aware script legitimately claimed the machine and was
about to start a run on top of it - the very contamination the lock exists to prevent, arriving
through the lock rather than around it.

"Does anyone else hold the right" and "is anyone else already working without asking" are different
questions. A lock answers only the first. While any script in the queue does not take the lock,
claiming the machine must also require that no model process is running - blunt, because at claim
time nothing of ours has started, so any model process at all belongs to someone else.

The general form: a protocol protects you only across the participants that speak it. Introducing
one does not retroactively enrol the code written before it.

## 41. Contamination only depresses a speed number, so a losing arm stays lost

Five arms of the speculation depth sweep were measured while another process held the machine, with
spreads of 26.3%, 19.3%, 16.1%, 28.4% and 52.8% against a 4.2% noise floor. The instinct was to
re-run them in silence. That would have been wasted machine time.

Contention takes bandwidth away from a run; it never hands any back. So each arm's *best* replicate
is an upper bound on what it would score clean. Those bests are 12.78, 10.47, 9.22, 10.23 and 9.44
tok/s, and the baseline measured cleanly at 14.04 with a 2.0% spread. Every upper bound is below
the baseline, so no re-measurement can reverse the verdict.

The general rule: before re-running a contaminated measurement, check which way the contamination
can push. If the dirty result already loses by more than the bound allows it to recover, the
conclusion is safe and only the number is unknown - and the number is not what was being asked.

## 42. The compiler is a participant too, and it must be judged by CPU time

Rule 40 said a protocol binds only the participants that speak it, and named the pre-lock scripts as
the ones outside it. It missed one: the build. A reference arm came in at 9.95 tok/s with a 34%
spread while cl.exe burned cores for a subagent's compile. The lock was held correctly, the
measuring script was the sole owner, and the machine was still not quiet.

So the claim check now also waits out active compiles - but by CPU-time delta over a sampling
interval, never by whether a compiler process exists. Judging compilers by existence is what froze
this queue for 2.5 hours: MSBuild keeps node-reuse daemons alive between builds and they consume
nothing. Both lessons have to be encoded together, because each one's naive fix reintroduces the
other's failure.

The pattern worth carrying: when you enumerate who might be using the machine, include the tools
you are using to change the machine, not only the tools you are using to measure it.

## 43. Check the machine at the claim, and you have checked it only at the claim

The lock was taught to wait out foreign compiles, and the very next arm came back at 6.45 tok/s
with a 111.5% spread - 9.82, 6.89, 2.63 - because the compile started *after* the claim succeeded.
A gate tests a condition at one instant; a measurement occupies an interval. Anything that can
begin during the interval is not covered by testing it at the boundary.

Continuous re-checking is the wrong fix here, because it only turns silent contamination into
detected contamination without producing a number either way. The right fix is to stop competing:
when the other work is on the critical path and the measurement is not, the measurement yields.
Contaminated arms are not cheaper than no arms - they cost the same machine time and produce
nothing.

What made this visible rather than silent was the spread flag, which refuses to call an arm a
reference when its replicates disagree by more than the 4.2% noise floor. That check earned its
keep twice in one evening: a mean of three disagreeing numbers looks exactly like a result.

## 44. A single replicate reports a perfect spread, and that is the absence of the check

An arm came back reading "11.59 tok/s (razbros 0.0%)" - the cleanest-looking line in the table. It
was one surviving replicate out of three; the other two produced no timing at all. Zero spread was
not evidence of a quiet machine, it was the arithmetic of having nothing to disagree with.

This is the same shape of error as judging compilers by existence and judging contention by free
memory: the check ran, returned a number, and the number described something other than what was
being asked. A spread test answers "do independent measurements agree" and it has no answer at all
below two measurements - so it must say so instead of computing 0.0%.

Every arm now refuses to report fewer than two replicates, naming the count instead. The general
form worth carrying: a summary statistic computed over too few samples does not degrade gracefully,
it degrades into a confident-looking constant.

## 45. The same case-insensitive collision, a second time - and a wrong diagnosis on the way

Every arm measured this evening reported one surviving replicate out of three, printed as a 0.0%
spread. The cause was `$p = Start-Process` inside a function whose prompt path lives in `$P`.
PowerShell does not distinguish case, so from the first assignment onward `-f $P` passes a Process
object where a filename belongs; replicate 1 succeeds and the rest die before they start.

This project has already lost a sweep to exactly this collision. Writing it down was not enough to
stop it recurring, because the note recorded the incident rather than the rule. The rule: in any
PowerShell function that reads a single-letter script variable, never name a local after it -
`$proc`, not `$p`. Rule 44's fix (refuse to report fewer than two replicates) is what made the
recurrence visible; it did not prevent it.

Worth recording separately: the first diagnosis was wrong. Sharing one redirect file across
replicates looked like an obvious culprit and a fix was written, committed and explained in a code
comment before checking whether the explanation held. It did not - spec_study.ps1 shares one file
across three replicates and gets three results, which was already on disk and took one look to
find. The comment asserting the false cause had to be removed from four files.

The check that was skipped: before fixing, find the case that should also be broken and confirm it
is. A cause that does not explain the working case is not the cause.

## 46. Tensor size from the gap to the next offset is right until it is catastrophically wrong

Sizes were being computed as the distance from one tensor's offset to the next. It is the obvious
method, it needs no type table, and it agreed with the file size. On Qwen3-Coder-30B it gave the
right answer to within 0.1%, and the whole plan for this hardware was built on its output.

On Coder-Next IQ4_XS it reported post_attention_norm.weight - a vector of a few thousand floats -
as 2967.8 MB, and put 88% of that model's per-token traffic into a category that does not exist.
The gap method silently assigns any unallocated space to whichever tensor precedes it, so a single
padding region turns one small tensor into a fabricated multi-gigabyte cost.

What caught it was not a checksum but an impossibility: a norm weight cannot be three gigabytes.
Had the same padding sat before an expert tensor, the number would have been merely wrong instead
of absurd, and nothing would have flagged it.

Sizes now come from shape and type through a block table, and a type missing from that table
yields a refusal rather than a guess - a wrong block size produces a plausible number, which is the
worse failure. The 30B's figures were re-derived under the correct method and held (static 802.2 MB,
47% of traffic), so the plan stands; but it stood on luck for several hours.

The general rule: prefer the derivation that can be wrong loudly. A method whose errors are always
plausible cannot be audited by looking at its output.

## 47. Sort the queue by whether a busy machine can corrupt the result, not by importance

Three speed measurements in a row were thrown away because subagents were compiling: 32%, 56.7% and
111% spreads against a 4.2% noise floor. The flag caught each one, so nothing false was reported -
but a flagged arm costs the same machine time as a good one and yields nothing, and it was run three
times knowing the agents were active.

The distinction that was missed: some measurements are corrupted by a loaded machine and some are
not. Timing is. Recording a router trace is not - its output is which experts the model chose, and
contention changes when that happens, never what it is. The same holds for correctness checks,
quantisation, and anything whose result is a value rather than a duration.

So the queue is sorted by that property. While other work holds the cores, run only what a loaded
machine cannot corrupt, and hold the timing arms for a quiet window. This is not the same as rule
43 (the measurement yields when it is not on the critical path) - that one is about priority, this
one is about which measurements even have the problem.
